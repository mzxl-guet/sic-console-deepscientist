# 「网页点发送就报错」的两个根因与修复记录

> 现象：在信通智研台网页里点「发送」，**立刻**弹回一条失败提示，内容只有一行
> `[WinError 2] 系统找不到指定的文件。`
> 连转圈都没有，说明请求在服务端**同步阶段**就挂了，跟模型、网络、翻墙都无关。

本文记录完整定位过程、两个独立根因、修复方式与回归验证。

---

## 0. 一句话结论

有两个彼此独立的坑，**都表现为同一个 `WinError 2`**，所以很容易误判成同一个问题：

| # | 根因 | 触发阶段 | 修复 |
|---|---|---|---|
| 1 | 服务进程的 `PATH` 里**没有 `git`** | 点发送 → 写消息 → 生成任务快照 | 把 Git 目录加进 `start.cmd` 的 `PATH` |
| 2 | `runners.yaml` 里 `binary: codex` 是**裸名**，Windows 下 `CreateProcess` 不会自动补 `.CMD` | 快照过了之后 → 拉起 runner | `binary` 改成 `codex.CMD` 的**绝对路径** |

第 1 个坑会让请求直接失败；修掉它之后，第 2 个坑才会露出来。**只修一个不够。**

---

## 1. 先排除的三个错误方向

排查初期最容易走偏，先把排除掉的记下来：

| 怀疑对象 | 排除依据 |
|---|---|
| codex 要翻墙 / OpenAI 账号 | `base_url` 指向 `https://api.deepseek.com/v1`，直连 **0.28 s** 返回 200 |
| 前端皮肤把页面改坏了 | 后端接口单独用 `curl` 打，同样报错，与浏览器无关 |
| 模型 key 失效 | 直接调 `/v1/chat/completions` 正常返回内容 |

**结论：故障在后端进程的执行环境，不在网络、不在模型、不在前端。**

---

## 2. 定位手法：把被吞掉的堆栈捞出来

接口的顶层异常处理是「把异常转成一行 message 返回」，堆栈被丢弃：

```python
except Exception as exc:
    self._write_json(500, {"ok": False, "message": str(exc)}, extra_headers=auth_headers)
```

`str(exc)` 对 `FileNotFoundError` 只会输出 `[WinError 2] 系统找不到指定的文件。`，
**不告诉你是哪个文件**。所以第一步是临时把它改成带堆栈：

```python
except Exception as exc:
    import traceback as _tb
    _detail = _tb.format_exc()
    with open(r"D:\DeepScientist\home\logs\http-error-debug.log", "a", encoding="utf-8") as _fh:
        _fh.write("=== " + self.path + " ===\n" + _detail + "\n")
    self._write_json(500, {"ok": False, "message": str(exc), "traceback": _detail}, ...)
```

> 定位完必须把这段改回去，否则等于在生产代码里留了个调试后门。
> 本项目已在修复完成后还原为原始实现。

## 3. 根因一：`PATH` 里没有 `git`

`POST /api/quests/{id}/chat` 的调用链是：

```
handlers.chat
  └─ app.submit_user_message
       ├─ quest_service.append_message      # 写消息，OK
       ├─ quest_service.snapshot            # ← 这里炸
       │    └─ 内部要读 git 分支/状态 → subprocess(["git", ...])
       └─ schedule_turn
```

**证据**：用与 `start.cmd` 完全一致的受限 `PATH` 跑一个探测：

```
git   -> None
        FAIL: FileNotFoundError [WinError 2] 系统找不到指定的文件。
codex -> C:\Users\18015\AppData\Roaming\npm\codex.CMD
node  -> D:\DeepScientist\node\node.EXE      ok: v22.9.0
curl  -> C:\Windows\system32\curl.EXE        ok: curl 8.21.0
```

`git` 直接被判定为「不存在」。

**为什么会这样**：`start.cmd` 为了让启动环境干净，把 `PATH` **整条重写**了：

```bat
set "PATH=D:\DeepScientist\node;D:\DeepScientist\npm-global;%SystemRoot%\system32;%SystemRoot%;%SystemRoot%\System32\Wbem"
```

这条 `PATH` 里既没有 Git，也没有 `%APPDATA%\npm`（codex 在那儿）。
而平时在终端里手动跑之所以正常，是因为继承了系统的完整 `PATH` —— **这就是「我这边好好的，你那边报错」的典型来源。**

**本机特殊情况**：这台机器上没有独立安装的 Git，唯一的 Git 是 WorkBuddy 自带的便携版：

```
D:\aiagent\WorkBuddy\resources\vendor\PortableGit\mingw64\bin\git.exe   (git 2.55.0)
```

**修复**：把 Git 目录写进 `PATH`，并加启动自检（见第 5 节）。

---

## 4. 根因二：`binary: codex` 裸名在 Windows 下必然失败

修掉 `git` 之后，同一条请求换了个错法 —— 仍然是 `WinError 2`，但现在是在**拉起 runner** 的阶段。

`config/runners.yaml` 原来是：

```yaml
codex:
  enabled: true
  binary: codex      # ← 裸名
```

Python 的 `subprocess` 在 Windows 上**不做 `PATHEXT` 扩展**。
`CreateProcess` 拿到一个没有扩展名的 `codex`，找不到同名可执行文件，直接 `WinError 2` ——
**哪怕 `codex` 就在 `PATH` 里、哪怕 `shutil.which("codex")` 能定位到它。**

实测三种调用方式（同一个文件 `C:\Users\18015\AppData\Roaming\npm\codex.CMD`）：

| 调用方式 | 结果 |
|---|---|
| `["C:\\Users\\18015\\AppData\\Roaming\\npm\\codex.CMD", "--version"]` | ✅ `codex-cli 0.147.0` |
| `["codex", "--version"]`（裸名，且在 PATH 里） | ❌ `FileNotFoundError [WinError 2]` |
| `"codex --version"`, `shell=True` | ✅ `codex-cli 0.147.0` |

**修复**：`binary` 改成绝对路径。

```yaml
codex:
  enabled: true
  binary: C:/Users/18015/AppData/Roaming/npm/codex.CMD
```

> 顺带说明：之所以上一轮"跑通过一次"，是因为当时用环境变量
> `DEEPSCIENTIST_CODEX_BINARY` 临时传了绝对路径，而 `start.cmd` 里并没有设它。
> 也就是说 **那次成功是不可复现的**，用户双击快捷方式必然失败。
> 这次把绝对路径落到配置文件里，才是可复现的修法。

## 5. 最终修复内容

### 5.1 `start.cmd`

```bat
set "PATH=D:\DeepScientist\node;D:\DeepScientist\npm-global;%APPDATA%\npm;%USERPROFILE%\AppData\Roaming\npm;D:\aiagent\WorkBuddy\resources\vendor\PortableGit\mingw64\bin;D:\aiagent\WorkBuddy\resources\vendor\PortableGit\cmd;%SystemRoot%\system32;%SystemRoot%;%SystemRoot%\System32\Wbem"
set "DEEPSCIENTIST_CODEX_BINARY=C:\Users\18015\AppData\Roaming\npm\codex.CMD"
```

并新增启动自检，缺依赖时**在窗口里直接说人话**，而不是等用户在网页上撞 `WinError 2`：

```bat
where git >NUL 2>&1
if errorlevel 1 echo   [!] 没找到 git，任务快照会报 WinError 2
if not errorlevel 1 echo   git: OK
where codex >NUL 2>&1
if errorlevel 1 echo   [!] 没找到 codex，发送消息会报 WinError 2
if not errorlevel 1 echo   codex: OK
```

### 5.2 `config/runners.yaml`

```yaml
codex:
  binary: C:/Users/18015/AppData/Roaming/npm/codex.CMD
```

### 5.3 附带发现：`--home` 必须写在子命令**前面**

排查途中还踩到一个容易忽略的点。`deepscientist.cli` 的 `--home` 是**全局参数**：

```
python -m deepscientist.cli --home "D:\DeepScientist\home" daemon --host ...   # 正确
python -m deepscientist.cli daemon --home "D:\DeepScientist\home" ...          # 错，会被当成 daemon 的参数
```

而且 `DEEPSCIENTIST_HOME` **这个环境变量根本没有被读取**，`default_home()` 是写死的：

```python
def default_home() -> Path:
    return Path.home() / "DeepScientist"
```

所以一旦漏写 `--home`，服务会去 `C:\Users\18015\DeepScientist` 起一个**空实例**：
网页能打开、接口返回 200，但 `/api/quests` 是 `[]`，所有任务都"不存在"。
更坑的是 `start.cmd` 的探活逻辑是「端口通就认为已在运行」，
于是**空实例会一直占着 20999，正确实例永远起不来**。

## 7. 复现清单

| 步骤 | 命令 / 位置 |
|---|---|
| 1. 确认 Git 可用 | `where git` 应输出一个路径 |
| 2. 确认 codex 绝对路径 | `where codex` 得到 `...\npm\codex.CMD` |
| 3. 写入 `runners.yaml` | `binary: <上一步的绝对路径>` |
| 4. 补全 `start.cmd` 的 `PATH` | 加 `%APPDATA%\npm` 与 Git 目录 |
| 5. `--home` 放在子命令前 | `... cli --home <HOME> daemon ...` |
| 6. 启动并验证 | `curl http://127.0.0.1:20999/api/quests` 应返回任务数组而非 `[]` |
| 7. 发一条消息 | 返回 `"ok": true` 且 `"started": true` |

## 8. 通用教训

1. **`[WinError 2]` 永远先怀疑"找不到某个外部程序"**，而不是"文件读不到"。
   Python 的 `FileNotFoundError` 在 Windows 上会把两种情况混在一起报。
2. **重写 `PATH` 是危险的**。启动脚本为了干净而整条重写 `PATH`，很容易把
   用户在终端里"明明能用"的东西弄丢。要么追加，要么在启动时自检并明确报错。
3. **Windows 下 `subprocess` 传裸名不可靠**。凡是要拉起第三方 CLI，写绝对路径。
4. **"上次跑通过"不等于"可复现"**。如果那次成功依赖了某个临时环境变量，
   就必须把它固化进配置文件，否则用户一重启就回到原点。
5. **探活不能只看端口通不通**。要看"是不是我想要的那个实例"——
   这次差点被一个指向空目录的假实例骗过去。
